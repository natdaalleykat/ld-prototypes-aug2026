# Foundation cross-product expansion: the refined exploration

Natalie Friedman · August 24, 2026 · Continues the August prototype. Everything below is grounded in the product codebase code and live flag state on the internal LD instance (citations in `research/`). Where a concept sounded good but the primitive doesn't work that way, the correction is called out inline.

## 1. Ground truths that reshaped the exploration

These came out of the code and live-flag research and they change what we should build:

1. **Every account already has 5 free guarded rollouts and nobody is told.** The usage-gated trial (the guarded-rollout limits config) gives 5 included, 2 grace, hard stop at 7, to effectively all customers regardless of plan. The counter is **lifetime**, it never resets, and the first time a user learns any of this is a warning banner inside the guarded form when they are already half-way through the allowance. There is a giveaway sitting in the product with no announcement.
2. **The "turn this rollout into an experiment" one-click is not how the primitive works.** Starting an experiment replaces the rule's rollout entirely; treatment allocations overwrite the user's 25/75. The rule's audience (clauses) is preserved, the split is not. There is no adopt-the-existing-split path anywhere, and building one is a statistics decision (underpowered control), not a UI task. Honest offer: "same audience, new measured split", never "keep your split and measure it."
3. **The machinery behind that offer already shipped.** "Create experiment from rule" (flask/kebab) is live for single-variation rules, and "Optimize → Experiment" in the serve menu is live for rollout rules (it clears the rollout and asks for a fallback). What's missing is not capability, it is **discovery**: both are buried in menus, and when a customer isn't entitled the options are invisible rather than upsold.
4. **O11y is the keystone product, not a side goal.** Autogenerated metrics from o11y telemetry (`otel.http.error` rate, 5xx rate, exception rate, latency) are live globally, and trace-based metrics are accepted by guarded rollouts in production (the code default says no; the live flag says yes). So: **an o11y-enabled account can guard a rollout with zero manual metric authoring.** O11y also gives experiments their "why did it lose" answer via replay. Getting o11y installed makes both other products radically cheaper to adopt.
5. **Enabling o11y is honestly "3 installs and one config block"**, in 6 languages only (JS, React, React Native, Vue, Node, Python). Never say "one line". Go/Java/.NET/Ruby accounts hit a dead end; gate the moment on detected SDK. Detection inputs exist (SDK versions per env, hourly; o11y-integrated boolean per project) but a min-version compatibility table does not; that's the one blocking dependency.
6. **Targeting the audience is already solved.** The dogfood account context carries the flags-only account attributes, `hasSessions`, `hasErrors`, `hasTraces`, an existing internal API, `planType`, `signupDate`. "Flags-only Foundation account, 30+ days in" is one LD segment rule, no backend work.
7. **The event store makes pre-matching real.** The app knows every custom event an account sends, per environment, with last-seen and which metrics already exist for each. "Your `checkout_completed` event is one click from a metric" is a query, not a dream.
8. **A complete cross-sell loop already runs for AgentControl**: targeted promo banner with 3-arm copy test → tracked click → Marketo lead field → nurture email. Cloning it per product is a catalog entry, a flag, and one 7-line map addition.
9. **Two purpose-built frameworks are sitting idle**: the Home page roadmaps for Experimentation and Observability are fully written behind the new-home gate (the New Home project), and onboarding-guidance has named-but-empty Experimentation and Observability flow groups plus an unmounted Starter guide. The welcome survey captures "observability" intent at signup and then never uses it.
10. **Archaeology says people tried before.** Six pre-cut analytics event names for guarded-rollout suggestions exist with zero call sites (an "available chip", an "add metrics suggestion", a save-time release-strategy step). A `session-replay-in-flag-audience` flag exists with zero consumers. Check the warehouse for whether these ever fired before minting new names, and ask the Guardian team why the UI was cut.

## 2. Goal: Experimentation

**Who is entitled:** Foundation and Developer plans have the experimentation gate on via plan segments. "Included in your plan" copy is true.

### Moments

| # | Moment | Type | Feasibility verdict |
|---|---|---|---|
| E1 | Percentage rollout configured: inline card under the rule (prototype moment 1) | Low friction + problem | **Green, small.** Card deep-links to the existing create modal, which already accepts flagKey + sourceRuleId as props. Copy must be honest per ground truth 2. |
| E2 | Rollout saved: same offer post-commit (prototype moment 2) | Problem | **Green, small.** A/B placement against E1. The save modal has a slot system; use an existing internal API as the trigger point. |
| E3 | Personalized empty state: their existing flags as experiment candidates | Killed | **KILLED, twice over.** First: flags-only customers never wander to the Experimentation empty state (no organic traffic). Second and fatal: the candidates were live flags whose users are already exposed, so converting them mid-flight produces contaminated results. Listing them as "ready to run" would be statistically dishonest. The salvageable piece (event-store personalization) moved into E4's metric drawer. |
| E4 | Add-metrics nudge on the flags list (prototype moment 4, rebuilt) | Low friction + problem | **Green, small.** Config-derived banner ("3 recent rollouts split traffic, nobody measured") plus a drawer of events the account already sends, each one click from a metric (prefilled metric-from-event creation ships today). Payoff framing is forward-looking: the NEXT release starts as an A/B test (included) or guarded rollout (5 included). Deliberately not retroactive, same exposure-contamination reason E3 died. Vega capability check: the flags-page Vega panel routes exactly two skills today (flag create, flag cleanup); retro case-study generation would be net-new AI work and needs user-initiated invocation anyway, so the deterministic version wins. |
| E5 | Experiment results → "watch replays of the losing variation" | Problem (also drives o11y) | **Yellow, medium.** No experiment link in o11y semantic conventions; derive via flag key + variation + iteration window. Breaks for holdouts/multi-flag. Undercount caveat: only sessions where the plugin saw the eval. See O3. |

### The engineer catches (the loop in action)

- Original moment 1 copy said "attach a metric and this rollout becomes an A/B test with the exact targeting you just set." Wrong twice: attaching a metric alone does nothing (that gesture belongs to guarded rollouts), and the traffic split gets replaced. Fixed copy sells "same audience, measured split, results from day one."
- "One click to a startable experiment" needs a metric, a hypothesis, and atomicity (a server-side composite create). "One click to a complete draft that lands on the design page with 1 or 2 fields left" is small and reuses the pending-experiment machinery. Ship the second, aspire to the first only if E1 click-through proves demand.
- An active guarded or progressive rollout excludes an experiment on that rule. Gate the card on rule state or the CTA lands on a blocked path.

## 3. Goal: Observability

**Who is entitled:** access is broadly enabled (waitlist only for high-risk accounts). Self-serve quotas are live for Developer 2025 and Foundation 2023 v3/v4. Session replay, errors, logs, traces are in the plans they already pay for.

### Moments

| # | Moment | Type | Feasibility verdict |
|---|---|---|---|
| O1 | SDK install time: "add observability while you're in the file" checkbox on setup snippets (prototype moment 6) | Lowest friction in the whole exploration | **Green, small-medium.** Snippets sync from the shared snippet source; the setup component is embeddable and prop-configurable. Direct precedent: the "Show code for Experimentation and Guarded releases" checkbox already shipped on SDK setup. Gate to the 6 supported languages. |
| O2 | Flying blind on a live rollout (rewritten prototype moment 3) | Problem | **Green, reframed twice.** First correction: without o11y there is no error data to spike, so an error-spike trigger is impossible for the target cohort. Second correction: accounts that set up errors almost always set up replay in the same sitting (the plugins install together), so "has errors, lacks replay" is not a cohort worth designing for. The real design question is where in the flag, experiment, and install lifecycles a zero-o11y account should meet session replay. Answer: all three, one build. Install time (O1), rollout-just-went-live on Monitoring where evaluations climb next to empty error/session panels (this moment), and experiment results (O3). Trigger for this one: active rollout with evaluations flowing plus no telemetry connected, both detectable today. |
| O3 | Guarded rollout regression / experiment result → session replays | Problem | **Green for rollouts (small): an existing internal API precedent makes an existing internal API a near-copy, and the flag query grammar ships today. Yellow for experiments (see E5).** |
| O4 | Welcome-survey o11y intent → actually route them | Low friction | **Green, small.** Intent is captured and explicitly discarded today (onboarding storage excludes the o11y path; flow registry TODO). Cheapest fix may be seeding the Home roadmap + a Marketo field. |
| O5 | Flag Monitoring tab empty o11y sections | Low friction | **Already built.** Setup instructions are already embedded there and copy events are instrumented. This is a measure-and-optimize surface, not a build. |

### The engineer catches

- The replay question is a lifecycle question, not a surface question: the same setup (both plugins, one config block) should be offered at install (O1), at rollout-goes-live (O2), and at experiment results (O3), with one shared destination and per-moment attribution. Don't build three setups.
- "One line to enable" dies on contact with the snippet: 3 installs, imports, and a plugins config block. The privacy default (`privacySetting: 'strict'`) is stated in the snippet and should be stated in the offer; replay pitches die without it.
- A compatible-SDK claim needs a min-version table that doesn't exist yet (source: the shared snippet source). Without it, gate on SDK name only and soften the claim.
- Any replay deep link must respect the regional sessions killswitch (the regional sessions killswitch) or we ship links that bounce with an error toast.

## 4. Goal: Guarded rollouts

**Who gets what (verified live):** every account: 5 included lifetime, 2 grace, hard stop at 7. Unlimited requires Guardian Edition. The option is visible to effectively everyone in the rollout mode picker. Requires at least 1 metric; o11y autogen metrics satisfy this with zero authoring (ground truth 4).

### Moments

| # | Moment | Type | Feasibility verdict |
|---|---|---|---|
| G1 | Rollout configured: "5 guarded rollouts are included in your plan" disclosure + Recommended tag on the guarded option (prototype moment 5) | Low friction | **Green, small.** The Recommended tag already renders; today only release policies drive it. Extending its input to a signal-derived recommendation was independently called the cheapest real win. |
| G2 | Toggle-on / ship-it: prompt a release with a guard | Problem | **Green, medium.** ToggleprefilledReleaseBuilder + ShipItButton + an existing internal API deep link all exist, but everything fires only when a release policy exists, which flags-only customers never have. The policy-less variant is the single highest-leverage change. Without a metric, prompt progressive and use the release builder's implicit upgrade: adding a metric IS the flip to guarded (0 metrics = progressive, 1+ = guarded), so no entitlement is spent until the user actually adds a guard. |
| G3 | O11y-enabled accounts: "guard this rollout with your error rate" using autogen metrics | Low friction + synergy | **Green pending one verification.** Trace metrics for RG are live, autogen is live globally. Verify autogen metrics actually materialize per account and carry a usable randomization unit before promising zero setup. |
| G4 | Post-incident retro: flag toggled off fast after toggle-on ("next time the flag reverts itself") | Problem | **Yellow, medium.** No flag-scoped error correlation exists outside a running guarded rollout. But the kill pattern (on, then off within minutes) is detectable from flag history alone. Honest version uses audit-log shape, not error data. |
| G5 | Trial exhaustion upsell | Conversion | **Already built** (usage alerts with Contact Us). Nothing to build; make sure the funnel is on a dashboard. |

### The engineer catches

- The counter is lifetime. A curious user who burns 3 of 5 on toy tests has permanently spent them. If we drive discovery hard, we also drive regret. Product ask for the Guardian team before any big push: reset annually, exclude sub-N-minute rollouts, or exempt obvious tests. Also confirm the sales narrative never says "per month."
- The guarded option stays selectable at the hard limit; users can configure everything and only then hit a blocked save. Any moment we build should check an existing internal API first.
- the measured-rollout backend event cannot distinguish guarded from progressive (no rolloutType property). Measurement for these moments needs the guarded-trial backend event (and note it also fires on blocked attempts; filter on `state`).
- Guardian trial copy says 14 days, the config default says 30. Confirm with billing before writing any dated copy.

## 5. The synergy thesis (what "cross product" actually means here)

The three goals are not parallel. There is an order:

1. **O11y install unlocks everything.** Auto error/latency metrics make guarded rollouts zero-setup (G3). Replay makes experiment results explainable (E5/O3). The cheapest install moment is when the user is already pasting SDK code (O1) or at signup when they told us they wanted it (O4).
2. **Guarded rollouts are the gateway drug to metrics.** A guarded rollout is "an experiment with training wheels": same mechanics (metric + randomization unit + traffic), zero statistics burden, and a free allowance. A customer who has run one guarded rollout has a metric, knows the canvas, and is one step from E1.
3. **Experiments are the destination**, and the in-flow moments (E1/E2) plus the metrics groundwork (E4) are how they get there. Always aimed at the NEXT release: converting flags that are already serving users produces contaminated results, so no moment ever offers to retrofit a running rollout.

So the portfolio isn't "three campaigns." It's one ladder: instrument (o11y) → guard (RG) → learn (experiments), with each moment nudging one rung.

## 7. The shortlist (what we believe will actually work)

1. **G1: tell people about the 5 free guarded rollouts, at the rollout moment.** A giveaway already exists; the entire feature is discovery. Cheapest honest claim in the portfolio.
2. **E1/E2: the rollout-moment experiment card**, honest copy, deep link to the existing modal with flag + rule prefilled. Machinery live, gap is discovery.
3. **O1: o11y at SDK install time.** The one moment enabling is nearly free, with a shipped precedent (the experimentation/guarded snippet checkbox).
4. **E4: the add-metrics nudge on the flags list**, with the event-store drawer (create a metric in two clicks from an event they already send) and the forward-looking payoff: the next release starts measured.
5. **G3: "guard with your error rate" for o11y-enabled accounts** once autogen verification passes. This plus O1 is the ladder working as designed.
6. **Lifecycle plumbing behind all of it**: Marketo map entries for first-rollout-configured, o11y-integrated, first-guarded-started; firstAction mismatch cohort emails.
